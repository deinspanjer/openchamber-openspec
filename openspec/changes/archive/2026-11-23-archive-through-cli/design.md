# Design

## Context

See proposal.md for motivation and specs/ for behaviour.

- The service runs the CLI through `runOpenSpec` (`src/service/cli.ts`), which appends `--json`,
  times out at 15 s and returns `{ ok: false, error: OPENSPEC_ERROR, value }` on a non-zero exit,
  keeping the parsed JSON in `value`. `src/service/http.ts` flags `mutationDispatched` so failures
  after a write are reported with `outcome: "unknown"`.
- `deleteChange` in `src/service/openspec.ts` is the pattern for a scoped mutation: `context()`
  with the expected root and planning, a fresh `list()`, `validatedChange()`, then the write.
- Observed `openspec archive <name> --yes --json` behaviour, on 2.0.0 and 2.1.0, against
  disposable roots:
  - Success exits 0 with `{ archive: { change, archivedAs, path, specsUpdated, totals, warnings? },
    root }`. A change synced exactly as its delta archives with `specsUpdated: false`. An
    already-absent REMOVED requirement adds a `warnings` entry.
  - Refusal exits 1 with `{ archive: null, root, status: [{ severity, code, message, fix? }] }`.
    Codes seen: `archive_spec_update_failed` (for example, an ADDED requirement that already
    exists because a sync reworded it, with "No files were changed"), `archive_tasks_incomplete`
    (only without `--yes`) and `archive_change_not_found`.
  - `--yes` also skips the incomplete-task check, so the service checks tasks itself.
- Upstream causes this works around: the `openspec-archive-change` skill always asks whether to
  sync when deltas are unsynced, and `openspec-bulk-archive-change` always asks for a selection and
  a confirmation. Both are generated by the OpenSpec CLI and can't be changed here.
- The SDK has no split button. `mountMenu` renders one labelled trigger with items;
  `src/panel/primary-action.ts` already pairs `mountButton` with `mountMenu` for Apply.

## Goals / Non-Goals

**Goals:**

- One service call archives a change. The panel decides only success, warnings, refusal or
  hand-off.
- Every outcome that is not a clean archive or a refusal reaches the agent with the raw CLI output.

**Non-Goals:**

- Reproducing the bulk skill's conflict resolution.
- Retrying an archive automatically, or reconciling a timed-out archive in the panel. The fallback
  prompt asks the agent to check.

## Decisions

### Service route `POST /archive`

Body: `directory`, `change`, `expectedRoot`, `expectedPlanning`, optional `skipSpecs: boolean`.
The adapter's `archiveChange`:

1. `context(directory, expectedRoot, expectedPlanning)`. Its errors pass through unchanged.
2. `list(directory, current)`. A missing change returns `CHANGE_UNAVAILABLE` (404). A zero task
   total or incomplete tasks return `CHANGE_INCOMPLETE` (409, "Tasks are incomplete. Refresh to
   see the current state.").
3. `validatedChange(current, change)`.
4. `checked(directory, ["archive", change, "--yes", ...(skipSpecs ? ["--skip-specs"] : [])],
   current)`. `http.ts`'s `checkedRunner` sets `mutationDispatched` when `args[0] === "archive"`.
   Reserve the CLI termination grace periods plus a small response margin inside the request
   deadline. If no execution budget remains, refuse before dispatch. A hard deadline can still
   expire with an unknown outcome; the hand-off must not claim the change stayed active.
5. Decode the result into a value. A CLI refusal is a normal response, not an HTTP error:
   - `ok` with an object `archive` whose `archivedAs` is a string →
     `{ outcome: "archived", archivedAs, warnings: string[] }`. `warnings` defaults to `[]` and
     must otherwise be an array of strings.
   - Anything else after step 4, including `OPENSPEC_ERROR` with or without `value`,
     `BAD_CLI_OUTPUT`, `CLI_TIMEOUT` or a `ROOT_CHANGED` report from `checked` →
     `{ outcome: "failed", command, output }`. `command` is the display string
     `openspec archive "<change>" --yes [--skip-specs] --json`. `output` is
     `JSON.stringify(value, null, 2)` when the CLI returned JSON, otherwise the error message,
     capped at 20 000 characters.

Steps 1 to 3 fail as ordinary service errors, and the panel shows them as error toasts. Only
step 4 onward produces a hand-off. This keeps refusals that an agent should not "fix", such as
unfinished tasks, out of the fallback prompt.

Alternative considered: run without `--yes` first and let the CLI refuse incomplete tasks. In JSON
mode the CLI also refuses spec updates without `--yes`, so this needs two runs per archive. The
pre-check reuses the listing every other route already decodes.

### Contracts and client

`src/contracts.ts` gains `decodeArchiveResult` for the two outcome shapes and fails fast on
anything else. `src/panel/client.ts` gains `archive(scope, change, { skipSpecs })`. No board-wide
reads change.

### Prompts

`src/panel/prompts.ts` replaces the archive branch of `actionPrompt` with
`archiveFallbackPrompt(failures)`, where each failure is `{ change, command, output }`:

```text
OpenSpec could not archive change "<change>" directly.

Command: <command>
Output:
<output>

Use your skill tool to load and invoke the openspec-archive-change skill for OpenSpec change "<change>". Fix the cause shown above, sync specs without asking if the change still needs it, and archive the change. Report what you changed.
```

For an uncertain result, tell the agent to check the active and archived locations before
attempting a fix. Do not compose a fallback for the explicit `archive without sync` action;
show its failure instead.

For several failures, one header line ("OpenSpec could not archive N changes directly.") is
followed by one Command/Output block per change and one closing instruction naming every change.
`src/panel/archive-prompt.ts` and `archiveAllPrompt` are deleted.

### Work Status chip (`src/status.ts`)

The `archive` stage chip calls `client.archive` with the card's scope and is disabled while
pending. Outcomes:

- archived: toast `Archived <change>.`, or `Archived <change> with warnings: <w1>; <w2>` as
  `info`, then schedule one section read.
- failed: `preparePrompt(change.id, archiveFallbackPrompt([...]), captureContext())` and toast
  `Couldn't archive <change>. A prompt to fix it is in the composer.` (`error`).
- service error: error toast with its message.

All feedback is gated on the captured context, as `preparePrompt` already is.

### Board single archive (`src/panel/controller.ts`)

`preparePrompt`'s `archive` intent becomes `archiveChange(change, captured, epoch, { skipSpecs })`
with the same staleness checks. Success reloads the board once, through the same path the panel
uses after its own create and delete. Failure composes the fallback prompt with current-chat
tracking.

### Split button (`src/panel/primary-action.ts`, `src/panel/detail-view.ts`)

`mountPrimaryAction` gets a Complete mode used only by the detail view: the existing `archive`
button, plus a `mountMenu` trigger in a separate root right after it. The trigger is labelled
`⌄`, with `aria-label="More archive actions"` set on the trigger button, and has one item,
`archive without sync` (id `skip-specs`). Board cards keep the plain button. CSS joins the two
controls with a 1 px divider and no gap between them.

### Archive all (`src/panel/controller.ts`, `src/panel/archive-dialog.ts`)

On confirm, the controller snapshots the available Complete change ids and calls `client.archive`
for each in turn, sequentially, so two changes on one capability apply in a fixed order. Before
each call it checks the captured context and stops when it changed. When the run ends in a current
context it:

1. Reloads the board once.
2. With failures, calls `host.startSession` with the existing `archive-all` provider data and the
   combined fallback prompt, and handles its result through the existing launch-outcome code.
3. Toasts `Archived N of M changes.` and adds `A session is fixing K failures (<sessionId>).` when
   one was started. Refusals count as neither archived nor failed and are listed by name.

Dialogue description: "This archives each completed change with the OpenSpec CLI, syncing specs
first. Unfinished changes are skipped. If any archive fails, a new session opens with a prompt to
fix it."

### Docs

- README: state that archiving requires OpenSpec 2.0 or later, and replace the bulk-archive
  sentence.
- AGENTS.md (Runtime boundaries): current-chat actions prepare drafts, except **archive**, which
  writes through `/archive`; **archive all** creates a session only for failures. Behaviour
  constraints: add "after the panel's own archive" to board loads and "after its own archive" to
  Work Status loads.

## Test seams

Agreed with the user: existing test files only, with no new files or helpers.

- `test/service.test.mjs`, real CLI against disposable roots (new CLI output): clean archive with
  synced specs, an already-synced change, the reworded ADDED failure decoding as `failed` with the
  CLI JSON, incomplete tasks refused without moving the change, and `skipSpecs` leaving main specs
  unchanged. A fake runner covers a timeout and non-JSON output decoding as `failed`.
- `test/panel.test.mjs`, fake SDK host with its fake `/archive` route: the Work Status chip
  (success toast and re-read with the composer untouched, failure composing the fallback prompt,
  service error toast), the board detail split button and `archive without sync` sending
  `skipSpecs`, the board card archive, and archive all (all succeed with no session, a mixed run
  with one session listing only failures, a context switch stopping the run).
- `test/contracts.test.mjs` only if `decodeArchiveResult` needs cases beyond the service tests.

## Risks / Trade-offs

- [CLI merge is stricter than the skill's agent merge] → Mismatches fail with "No files were
  changed" and go to the agent with the exact header.
- [A timed-out archive may have completed] → The fallback prompt carries the timeout and asks the
  agent to check before acting. The panel makes no claim either way.
- [Archive JSON shape changes in a future CLI] → Undecodable output is a hand-off, never a
  success.
- [The 15 s command timeout on large spec trees] → Accepted. A timeout is a hand-off.

## Migration Plan

Ship in one release. Rollback is reverting the change; no data or manifest migration.
